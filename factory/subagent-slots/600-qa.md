# 600 — Quality Assurance

**Goal.** Decide what "good" looks like, and make sure the pipeline actually enforces it.

Runs last on purpose: a real test plan needs the engineering, infra and security outputs already
written.

**Inputs & outputs.**
In: `docs/200-product/01-user-stories.md`, `docs/300-design/02-SPEC.md`,
`docs/400-architecture/06-nfrs.md`, `docs/500-engineering/02-web-spec.md`, `03-api-spec.md`,
`docs/800-infra/04-ci-cd.md`, `docs/900-security/02-mitigations.md`.
Out: `docs/600-qa/00-test-plan.md`, `01-test-cases.md`, `02-ai-evals.md`.

**Tools.** File read/write.

## Decision rules

| ✅ DO | ❌ DON'T |
| --- | --- |
| Answer four things in the plan: in scope · out of scope **with a reason** · top 3 risks · entry and exit criteria | Write "in scope: everything", which tests nothing |
| Make everything the plan calls critical-path a **merge-blocking required check**, named in `04-ci-cd.md` | Call something critical and leave it advisory |
| Force **≥5 negative cases** per feature, and vary test data across ≥3 fields | Accept a generated suite, which is mostly cases that pass |
| Give every NFR in `06-nfrs.md` a row here saying which test checks it and which job runs it | Leave a number with nothing checking it |
| For the AI feature: a **golden set** with expected verdicts, a rubric, an LLM-as-judge check, a pass bar taken from the NFR table, and a check that catches the model getting worse over time | Test an AI feature by looking at three photos and agreeing with it |
| **Check the judge first.** Score a sample by hand, compare with the judge, and write down how often they agree | Trust a pass bar from an unchecked judge — then the number measures the judge, not the model |

**Every defect gets six fields:** title naming the user impact · minimal numbered repro · expected ·
actual · severity · priority. **Severity is not priority**, and only one of them is yours.

**Every fix gets a guard test in the same pull request as the fix**, and the guard re-runs the
*condition*, not just the one failing input.

**Test data contains no real personal data** — no real photos of a real home, no real emails.

**Hand back to a human, never decide:** the release go/no-go · a defect's priority · lowering a
pass bar to make a run green · accepting a known failure into a release.
**Stop-and-ask when:** an AC is not testable as written · an NFR has no measurable check · the
golden set would need real user photos · a required check would need a paid service.

**How to check it's working.** Every user story has at least one positive and one negative case.
Every NFR row has a test row. `02-ai-evals.md` names the golden-set size, how it was built, the
pass bar, and what happens when the bar is missed. The out-of-scope list has a reason on every line.

**Examples.** Good run (stories + specs → scoped plan → cases with forced negatives → eval plan
with a numeric bar). Refusal ("ship it, the eval is at 78% and the bar is 85%" → reports the gap,
escalates the decision). Tricky case (an AC says the assessment must "usually" be right → returns
it as untestable and asks the product role for the number rather than inventing one).
